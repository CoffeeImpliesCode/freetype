### The release tarball's sha256 is not recorded, and this file does not invent one

The download index was read on 2026-10-05. For this release it lists
`freetype-2.14.3.tar.gz` and `freetype-2.14.3.tar.xz`, both dated
`2026-Mar-22 15:20`, and beside each one **only a detached `.sig` file**. It
publishes no checksum of either archive, so there is no digest to copy out of
it; and nothing in this workspace records which of the two archives this tree
was imported from, or the digest of either.

That is the honest state of the record, and the gap is a named prerequisite
rather than a filled-in guess: a digest that was never observed would be a
fabricated identifier in the one field whose purpose is to be unguessable. The
driver owns downloads, so re-fetching the archive, computing its sha256 and
adding it to this table and to the header of
[`UPSTREAM.sha256`](UPSTREAM.sha256) is the driver's step; it is listed in
[`FORK-NOTES.md`](FORK-NOTES.md) as an open item. A consumer who needs a
byte-level pin today can verify this tree itself: the 854 per-file digests in
[`UPSTREAM.sha256`](UPSTREAM.sha256) are what this SDK actually builds, and
`tools/check-provenance.sh` checks them plus the exact file set.

There is no VCS import and therefore no commit SHA: this SDK is built from a
release tarball, not from a clone. See "Import mechanism".

## What upstream is

A complete, self-contained implementation of a TrueType and OpenType font
engine: the TrueType, Type 1, CFF, CID-keyed, PFR, Type 42, Windows FNT, PCF,
BDF and SFNT drivers, the auto hinter and the PostScript hinter, four
rasterizers, a compressed-stream module that carries its own inflate, the
public C API and the internal headers behind it. It has no required external
dependency in the configuration this SDK builds: the optional ones — zlib,
libpng, bzip2, brotli, HarfBuzz — are each behind a macro that
`include/freetype/config/ftoption.h` ships undefined, and this SDK leaves them
undefined. See "What is not compiled, and why".

Upstream ships several build systems — GNU make, autotools, CMake, meson, plus
Visual Studio and Visual C project files and a VMS makefile — and this SDK
executes none of them. `build.zig` compiles the same C from the same
`modules.cfg`; see README.md, "Native-build deviations".

## The core closure, as upstream lists it

`modules.cfg` is upstream's own statement of what a library is made of, and
`meson.build:82-135` derives the source list from it. Both are read out of the
files rather than re-derived here.

* **Font drivers** (`FONT_MODULES += ...`, `modules.cfg:35-74`, ten): `truetype
  type1 cff cid pfr type42 winfonts pcf bdf sfnt`
* **Hinting modules** (`HINTING_MODULES += ...`, `modules.cfg:82-85`, two):
  `autofit pshinter`
* **Rasterizers** (`RASTER_MODULES += ...`, `modules.cfg:97-106`, four): `smooth
  raster svg sdf`
* **Auxiliary modules** (`AUX_MODULES += ...`, `modules.cfg:116-150`): `cache
  gzip lzw bzip2 psaux psnames`, of which this SDK compiles four — see the next
  section
* **Base extensions** (`BASE_EXTENSIONS += ...`, `modules.cfg:160-239`,
  sixteen): `ftbbox.c ftbdf.c ftbitmap.c ftcid.c ftfstype.c ftgasp.c ftglyph.c
  ftgxval.c ftmm.c ftotval.c ftpatent.c ftpfr.c ftstroke.c ftsynth.c fttype1.c
  ftwinfnt.c`. These are *not* unity units: `modules.cfg` names them one by one
  and each is its own translation unit in every upstream build system.

Two units sit outside that list, and upstream names both of them:
`src/base/ftbase.c:21-38` is the base unity unit, including the eighteen files
it owns, and `src/base/ftinit.c` is what walks `FT_CONFIG_MODULES_H` at
start-up. `include/freetype/config/ftheader.h:162-163` is what resolves that
macro to `<freetype/config/ftmodule.h>`, and that shipped file — not
`modules.cfg` — decides what a live `FT_Library` gets:
`include/freetype/config/ftmodule.h:13-31` holds nineteen registrations, nine
drivers, five modules and five renderers. `modules.cfg:116` lists
`AUX_MODULES += cache`, and the shipped list does not register
`ftcache_module_class` at all, so compiling `src/cache/` would add a module no
live library ever instantiates. `build.zig` follows the shipped list.

The public headers are the 46 `meson.build:139-184` lists. That file is the
authoritative list, and this SDK's installed set is exactly that list plus
`include/ft2build.h`, which upstream installs separately as the entry point
included by bare name. All 47 go under one directory here, so
`-I<includedir>/freetype2` alone satisfies the recipe
`include/freetype/freetype.h:58-61` gives.

## What is not compiled, and why

Four things travel and are not compiled, each for a reason that is a fact about
this configuration rather than a decision about the source:

* **`src/cache/`** — see above: `modules.cfg` lists it, the shipped
  `ftmodule.h` does not register it. The header `include/freetype/ftcache.h` is
  still installed, so a consumer can see that the API exists and is not backed
  by this build.
* **`src/bzip2/`** — `FT_CONFIG_OPTION_USE_BZIP2` is undefined, as
  `include/freetype/config/ftoption.h` ships it.
* **The PNG and WOFF2 shims** — `FT_CONFIG_OPTION_USE_PNG` and
  `FT_CONFIG_OPTION_USE_BROTLI` are undefined, so `src/sfnt/pngshim.c` and
  `src/sfnt/sfwoff2.c` compile to nothing. They are still *compiled* as part of
  the `sfnt` unity unit, which is the point: "contributes nothing" is a fact
  about the code, not about this graph leaving a file out.
* **`src/dlg/`** — upstream's own meson build does not compile it either:
  neither `modules.cfg` nor `meson.build` names it. The debug logger is used
  only when a debugging build is configured.

The result is a library that links no system zlib, no libpng, no bzip2, no
brotli and no HarfBuzz, and that exports no symbol from any of them.

## The shared object this SDK delivers

`builds/unix/configure.raw:20` states `version_info='26:6:20'`, which libtool
reads as current 26, revision 6, age 20, and `docs/VERSIONS.TXT:63` records the
same release beside `26.6.20`. The SONAME component is `current - age` = 6, so
upstream's installed object is `libfreetype.so.6`, and libtool's file name
would be `libfreetype.so.6.20.6`.

`build.zig` hands Zig `.{ .major = 6, .minor = 26, .patch = 20 }`, which yields
the **same SONAME**, `libfreetype.so.6`, and a versioned file name of
`libfreetype.so.6.26.20`. So: the SONAME a runtime loader is given is upstream's
and a consumer that links `-lfreetype` or opens `libfreetype.so.6` gets this
build; the versioned file *name* is not libtool's, and a consumer that hard-codes
`libfreetype.so.6.20.6` would not find it. That is a real boundary and not a
detail, and README.md says so in the same place it lists the export surface.

## The upstream test material, and what it is not

The release's `tests/` holds one regression program, not a conformance suite:

* `tests/meson.build:1-12` builds `issue-1063/main.c` and registers exactly one
  `test()` target in the `regression` suite, and `tests/meson.build:6-7` points
  it at a `FREETYPE_TESTS_DATA_DIR` it does not ship.
* `tests/README.md:5-8` says the fonts have to be downloaded first, by
  `tests/scripts/download-test-fonts.py`, the only script in the directory.
* Building those tests needs meson and the `tests` option enabled
  (`tests/README.md:10-17`), neither of which this SDK runs.

Two consequences are binding here. This SDK does **not** claim to ship, build
or run an upstream test suite, and no build step fetches fonts or a harness to
stand in for one: a fetched font set is not part of the release this SDK pins,
and a fetched one would have no recorded digest. The SDK's own behavioural tests
are independent known answers against a vendored fixture and are described in
README.zig.md.

## Nothing is generated at build time

This SDK generates nothing from upstream's build: no configure step runs, no
Makefile is written, and no header is produced. The two files upstream *does*
generate are handled rather than reproduced:

* `devel/ft2build.h` and `devel/ftoption.h` are generated by upstream's `devel`
  target, which the release runs before packaging (`builds/toplevel.mk:252-256`),
  so they arrive already built and are digested here.
* `freetype2.pc` is written by autotools at install time and does not exist in
  the release. `build.zig`'s `add_pkg_config` writes it, relocatable through
  `${pcfiledir}`, with every field traceable to an upstream line.

## Import mechanism

A release tarball, imported whole. There is no upstream Git history in this
tree, no commit SHA to record, and no patch series: the tree either matches the
release or a deviation is recorded. `UPSTREAM.sha256` plus the exact-file-set
check in `tools/check-provenance.sh` is what makes that checkable rather than
asserted.

The upstream VCS tag for this release is `VER-2-14-3`, which is what a re-sync
would merge; the archive and the tag are two routes to the same tree, and this
one is an archive import with no history.

If a future wave re-syncs to another release, the correct sequence is: download
the new archive, verify its published digest, replace the imported files,
update `UPSTREAM.sha256`, `UPSTREAM.md`, `NOTICE.md` and `README.md`, and add a
numbered `CHANGELOG.md` entry — in one change.

## Third-party material in this repository

One file, and it is the fixture this SDK's own tests decode:

* `tests/fixtures/HarfBust.ttf` — HarfBuzz's own Latin in-house test font,
  vendored from `harfbuzz/test/shape/data/in-house/fonts/` of HarfBuzz 14.5.1
  under the SIL Open Font License 1.1, whose text is beside it as
  `tests/fixtures/COPYING`. Its sha256 is
  `116106c52c9c4b101497bd3aaf973d3b4e265658151d36db9aff412201bd4d29`, and
  `tests/fixtures/HarfBust.ttf.gz` is the same font compressed, beside it. All
  three digests are recorded at the end of
  [`UPSTREAM.sha256`](UPSTREAM.sha256) and re-checked by
  `tools/check-provenance.sh`.

Nothing else. The inflate implementation under `src/gzip/` looks like vendored
third-party code and is not carried by this fork at all: it is upstream's own
bundle, described by `src/gzip/README.freetype:16-22` as unmodified zlib 1.3
source with a patch applied, and `src/gzip/zlib.h:1-29` carries zlib's own
licence. The four HarfBuzz-derived headers under `src/autofit/` are likewise
upstream's own material under the 'Old MIT' terms, not a copy this fork made;
NOTICE.md records both.
